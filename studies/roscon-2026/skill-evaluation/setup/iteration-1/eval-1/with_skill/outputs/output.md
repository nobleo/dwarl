No—not as a drop-in policy, and not as a three-controller MuJoCo comparison. Another robot’s policy needs a matching frozen robot/observation/action contract; merely loading its weights proves nothing. Train for Rover’s actual geometry and sensing unless compatibility is established. MPPI and DWB comparisons require Gazebo; MuJoCo evaluation is DWARL-only.

## Setup/check sequence (instructions only; nothing launched or edited)

1. **Locate and inspect Rover’s assets.** Under `/robots/rover`, identify the URDF/Xacro, meshes, description packages, integration profile and ROS launch files. Use the exact integration directory or `dwarl_robot.yaml`, not an ambiguous workspace root. Preserve existing models and policies. Follow `docs/integrate-robot.md` and the existing profile template/schema.
2. **Establish the robot contract.** Confirm wheel joints, radius/separation, inertials/supports, physical footprint, base/odom/map frames, velocity and acceleration limits, control period, scan topic/range/post-filter angular coverage/ray count/history, and odometry interface. Do not substitute another robot’s footprint or use costmap inflation as physical geometry.
3. **Resolve the lidar and command details before training.** Verify the full base-to-lidar transform in the URDF and runtime TF: the measured upside-down rotation and +0.3 m forward translation both matter for ray directions and footprint clearance. Confirm transformed scan angles with known obstacle positions. Retain the actual front-only coverage; reprojection and rear collision-monitor polygons cannot reveal rear obstacles. Explicitly address unobserved reverse/recovery motion. Set the eventual profile’s `ros.cmd_vel_stamped: true` and actual command topic, and verify TwistStamped compatibility through controller → `cmd_vel_raw` → collision monitor → driver/mux.
4. **Validate the integration before any training.** Once a correct profile exists, the documented checks are:
   ```bash
   dwarl doctor --sim mujoco
   dwarl robot check "$INTEGRATION"
   dwarl robot view "$INTEGRATION"
   dwarl train "$INTEGRATION" --print-config
   dwarl train "$INTEGRATION" --dry-run
   ```
   These are proposed future commands, not executed here. Inspect mass, wheel geometry, lidar pose, spawn height and stable floor support. The viewer is a model check, not navigation evidence.
5. **Freeze inputs and train a bounded Rover run.** Record source revision, profile/assets and resolved configuration. Generate/check robot-sized dataset metadata and keep training, validation and held-out test splits separate. Start with a small pipeline smoke run, then a declared training budget. Intermediate validation, early stopping and compute profiling are optional, disabled by default; if enabled, validation intervals must be multiples of checkpoint save interval, with patience/minimum gain recorded. Resume restores the old recipe; changed geometry, sensing or rewards calls for a new run.
6. **Evaluate one exact checkpoint in MuJoCo first.** Pin its iteration/hash and use a small balanced validation set, DWARL only, at most 32 cases by default. Select on validation; `best` requires completed validation evidence. Read summary/episodes and individual trajectories, motion traces, collisions and footprint clearance. Reserve held-out cases for the final frozen selection. A completed command or smoke run is not proof of successful navigation.
7. **Export and verify the whole deployment bundle.** Test/deploy automatically export; there is no separate `dwarl export`. Check deployment with `dwarl deploy "$INTEGRATION" --run "$RUN" --checkpoint <iteration> --dry-run` before eventual installation. Keep ONNX, `deploy.yaml`, robot identity, frozen assets, configuration and checkpoint/provenance hashes together. Verify runtime parity and recorded-input replay where available, including scan preprocessing and action mapping. Desktop replay latency is not robot CPU performance.
8. **Prepare Gazebo before requesting three controllers.** If the same run should support Gazebo, plan its adapter and `ros.sim_launch` before training freezes the contract. Source ROS Jazzy, the built Rover workspace and DWARL’s ROS overlay; install Nav2 MPPI/DWB. The robot-only adapter must accept `world`, `x`, `y`, `yaw`, `gui`; publish clock, scan, odometry and correct TF; accept TwistStamped; spawn entity `robot`; use zero-at-spawn odometry; preserve ROS domain/Gazebo partition. DWARL supplies navigation/localization for managed cases, so avoid duplicate stacks. A later interface change requires a new run rather than editing saved contracts.
9. **Smoke Gazebo, then compare sequentially.** After readiness checks, run one case first. Only then request a bounded matched validation comparison, for example:
   ```bash
   dwarl test --run "$RUN" --checkpoint <iteration> --suite validation \
     --sim gazebo --controllers dwarl,mppi,dwb --set test.max_cases=3
   ```
   This means three cases per controller, nine executions. Freeze case IDs, stack and controller parameters; match footprint, limits, control rate, planner, scoring and safety settings. Examine actual commands/motion, clearance, safety-monitor/recovery behavior and localization differences; recovery mechanisms differ across controllers. Read launch logs and parameter snapshots, audit with `uv run python scripts/audit_comparison.py <test-directory>`, and repeat promising validation results before final held-out testing. Enable compute profiling only explicitly and separately from training. Simulator results do not establish physical-robot performance.
