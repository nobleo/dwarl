No—not without checking policy compatibility and validating the robot and simulator contracts first.

1. **Inspect and freeze the robot contract.** Inventory `/robots/rover`: URDF/Xacro, meshes, joint names, wheel radius/separation, footprint, velocity/acceleration limits, frames, odometry, scan and command topics. Record source revision, configuration and any candidate checkpoint/hash; preserve existing artifacts.
2. **Correct lidar geometry.** Encode the actual mounting transform from `base_link` to the scan frame: +0.3 m forward, measured height and the actual upside-down rotation. Verify TF and transformed scan points against known obstacles on both sides. Do not merely reverse ranges or change the frame label. Account for the sensor origin when measuring robot clearance.
3. **Make front-only visibility explicit.** Match scan angles, ordering, range limits, invalid-return handling, sampling and observation size to training/deployment preprocessing. Unobserved rear sectors are unknown, not free space. Check the policy’s field-of-view assumptions; restrict reverse motion/recovery into unseen space or provide suitable sensing and validated safety coverage.
4. **Match the command interface.** Ensure the deployment output or explicit adapter publishes `geometry_msgs/msg/TwistStamped` on the robot’s expected topic, with valid timestamps and the required frame convention. Check ROS time, QoS, command limits, watchdog and stop behavior. Avoid competing command publishers and verify the complete controller → safety → base chain supports the chosen message type.
5. **Decide policy compatibility.** Compare the other robot’s saved recipe and observation/action contract with Rover’s geometry, sensing, limits and preprocessing. Matching tensor dimensions alone is insufficient. Treat a compatible checkpoint as an unproven transfer candidate; otherwise train a Rover-compatible policy with `dwarl train`. Resume preserves the saved recipe; changed observations or rewards require a new run.
6. **Validate the simulator adapter before evaluating.** Verify that the MuJoCo path actually supports Rover and every requested controller, including any ROS/Nav2 interfaces they require. Check wheel/actuator mapping, units, physics timestep, scan/odometry generation, reset semantics and command stamping. Smoke-test forward motion, turning, stopping, scan orientation and collision/clearance measurements. Do not assume importing the model provides a complete navigation benchmark.
7. **Start with a small DWARL-only validation run.** Use `dwarl test` with explicit Rover configuration and inspect summary, episodes, traces, parameter snapshots and logs. Check actual goal completion, collisions, minimum clearance and safety/recovery behavior. Default testing stays DWARL-only, with at most 32 balanced cases; intermediate training checks and compute profiling remain disabled by default.
8. **Then opt into the three-controller comparison explicitly.** Name the controllers and verify each backend is available. Freeze checkpoint, robot contract, case IDs/seeds, simulator, source revision, scoring and stack settings. Keep common global-planning, sensing and safety/recovery conditions matched; document controller-specific differences. Declare hypothesis, acceptance criteria and trial budget, tune only on validation and repeat promising results on identical cases. Run simulation trials sequentially; never rebuild a controller library used by a live worker.
9. **Audit and report honestly.** Audit the test directory with `uv run python scripts/audit_comparison.py <test-directory>`, freeze selected settings, then evaluate held-out cases. Report success, collisions, clearance and recovery along with any explicitly enabled compute measurements and their boundaries. MuJoCo results do not establish Gazebo or physical-robot performance; verify the selected policy in Gazebo before promotion and validate deployment through `dwarl deploy` with controlled low-speed robot checks.
